# Chess Solver — Progress

## v1.1.1 (2026-09-24): Windows launch fix
- v1.1.0 .exe did nothing on launch. Two causes: (1) a listen error other
  than EADDRINUSE on the fixed port (Windows returns EACCES for ports in
  Hyper-V/WSL/Docker excluded ranges) rejected startServer unhandled, so no
  window was created but the process lived on, holding the single-instance
  lock and making every later launch exit silently. Now any listen error
  falls back to a random port, and a total failure shows an error box and
  exits. (2) Electron's BrowserWindow doesn't honor COOP/COEP
  (crossOriginIsolated stays false), so SharedArrayBuffer was undefined and
  the multi-threaded engine never started; fixed with
  app.commandLine.appendSwitch('enable-features', 'SharedArrayBuffer').
  Both verified in real Electron under Xvfb (engine runs 3 threads, ~1M
  nps; port-taken fallback; second-instance handoff).
- Portable .exe shows build/splash.bmp while it unpacks (~320MB per launch).

## v1.1.0 (2026-09-24): engine speed/strength + reliability audit
- The app had been shipping the SINGLE-threaded Stockfish build
  (public/stockfish.* byte-matched stockfish-18-single), so the Threads
  option was silently ignored. Now uses the multi-threaded NNUE build
  (stockfish-18.js/.wasm), ~4x nodes/sec on a 4-core machine.
- Engine files are no longer committed (no more Git LFS): vite.config.ts's
  stockfish-engine plugin serves them from node_modules/stockfish/bin in dev
  and copies them into dist/ on build.
- Root cause of "no move after moving quickly": the worker queues `go` while
  a search is still unwinding but runs `stop` immediately, so the stop could
  be lost; the 3s stop watchdog then restarted the engine (recompiling
  113MB) and analysis failed. Reproduced in Chromium (16 of 35 rapid
  positions got no analysis). Fix: `stop` is re-sent every 100ms until its
  bestmove; stop watchdog raised to 8s; startup waits for readyok after
  Threads/Hash; redundant ucinewgame dropped (warm start ~3.5s to first
  move). Regression test in src/engine/stockfish.test.ts with a fake worker
  that mirrors the real queueing.
- Hash stays 512MB: 1GB intermittently crashes the 2GB WASM heap. Threads
  capped at 8 (32 hangs the build).
- Think time setting (1/3/5/10s) in the settings menu.
- Update check now also runs automatically at startup (toggle in settings);
  a banner + gear dot show when a newer release exists, dismissible per
  version (src/useUpdateCheck.ts).
- Electron: fixed port 47813 (random fallback) so localStorage settings
  persist across launches and Chromium's WASM code cache works; files are
  streamed with ETag/no-cache; single-instance lock.
- Fonts bundled via @fontsource (Google Fonts was blocked by the app's CSP
  and COEP in Electron).

## Current state (2026-07-08): v1.0.0 release prep
- Engine layer (src/engine/stockfish.ts) rewritten around bestmove accounting:
  no readyok/isready synchronization, pending analysis survives engine
  restarts, stuck searches auto-retry once on a fresh worker, and worker
  startup has a 20s uciok timeout. This fixed the long-standing bug where
  moving before the best move loaded left the other side's analysis stuck
  until several refreshes.
- App state (src/App.tsx) refactored to derived data: turn, game end, opening
  name, and legality warnings derive from the FEN; analysis results are keyed
  by the FEN they were computed for, so stale engine output can never render
  against the wrong position.
- FEN editing helpers extracted to src/engine/fen.ts (unit-tested).
- Settings gear (top left) with version display, GitHub link, and
  "Check for updates" backed by the GitHub releases API (src/engine/updates.ts).
- Electron hardening: path-traversal fix (separator-suffixed prefix check),
  CSP + nosniff headers on the local server, sandbox enabled,
  setWindowOpenHandler/will-navigate guards (external links open in browser).
- CI: .github/workflows/ci.yml runs lint, vitest (42 tests), and build on
  push/PR to master. LFS deliberately not fetched in CI.
- README rebuilt with logo (docs/logo.png, extracted from build/icon.ico),
  badges, and test docs. MIT LICENSE added. GitHub topics set.

- MultiPV selector: 1 (default, deepest), 3, 5.

  recreates window on Dock activate).
- build/icon.png (1024px, from build/make-icon-png.ps1) feeds the .icns.
- .github/workflows/release.yml builds the Windows portable exe and a
  universal (x64+arm64) .dmg on tag push, or via workflow_dispatch against
  an existing release tag. Checkout uses lfs: true (packaging needs the

## Packaging size fix (2026-09-23, branch fix/packaging-size)
- Symptom: downloaded v1.1.0/v1.1.1 portable .exe showed the NSIS splash,
  then no window. Dev mode, a local package, and the *actual released*
  v1.1.1 artifact all launch correctly on the dev machine, so this was
  never a hard crash.
- Root cause: electron-builder always packs production node_modules
  regardless of the "files" list. The asar carried all six Stockfish
  builds from node_modules/stockfish/bin (~360MB) plus the 113MB copy in
  dist/ that is the one actually served. With win.target = "portable"
  the whole payload re-extracted to %TEMP% on EVERY launch (measured
  637-709MB), leaving no window on screen for tens of seconds.
- Fix: added "!node_modules/**/*" to build.files. Safe because nothing
  loads from node_modules at runtime (main.cjs uses only electron + node
  builtins; Vite bundles the renderer into dist/).
    app.asar 490MB -> 114MB | portable 390MB -> 162MB | %TEMP% 709 -> 452MB
- Verified after repackaging: window in ~10s, server on :47813, and
  "[Stockfish] Engine ready (Threads=3, Hash=512MB)" in the packaged build.
  45 tests pass, lint clean.

## Known quirk: single-instance lock can silently eat launches
- app.requestSingleInstanceLock() -> app.quit() means a launch while an
  earlier instance is still unpacking dies silently (splash, then nothing).
  In v1.1.0 a failed startServer() left a windowless process alive forever
  holding that lock, blocking every later launch including v1.1.1.
  v1.1.1 fixes the cause but cannot evict an already-running v1.1.0 zombie.

## v1.1.2: Windows switched from portable to NSIS installer (2026-09-23)
- win.target changed "portable" -> "nsis". The portable target re-unpacked
  the whole payload to %TEMP% on EVERY launch; nsis unpacks once at install.
- nsis config: oneClick false (assisted, user picks the directory),
  perMachine false (installs to %LOCALAPPDATA%\Programs\Chess Solver, so no
  UAC prompt for the unsigned binary), desktop + Start Menu shortcuts,
  installer/uninstaller icons from build/icon.ico.
- build/splash.bmp deleted: its only consumer was portable.splashImage.
- Measured on the installed app, cold start, no other instance running:
    window + "[Stockfish] Engine ready (Threads=3, Hash=512MB)" in under 2s
    (was 10-15s), and 0 bytes extracted to %TEMP% (was 637-709MB per launch).
- Installer verified end to end: installs to %LOCALAPPDATA%\Programs\
  Chess Solver (452MB on disk, once), writes desktop + Start Menu shortcuts,
  registers "Chess Solver 1.1.2" under HKCU uninstall with a /currentuser
  uninstall string. It also overwrote the stale hand-made desktop shortcut
  that still pointed at the abandoned %LOCALAPPDATA%\ChessSolver build.
- Windows download: 304MB (v1.1.1) -> ~165MB.
- README: download/build sections rewritten; the manual Copy-Item +
  WScript.Shell "install as desktop app" recipe removed (the installer
  does that now, and that recipe is what created the stale install).
- updates.ts reads only tag_name/html_url, so renaming the Windows artifact
  to "Chess Solver Setup <version>.exe" does not affect the update check.

## v1.1.3: window fits its content; lock failures are no longer silent (2026-09-24)
- Window sizing: createWindow now opens with show:false, waits for
  did-finish-load, measures the .app element's bottom, and setContentSize()s
  to that (+24px gutter) clamped to the display work area, then centers and
  shows. Measured need is 1100x850; the old default was width/height
  1100x750 *outer*, i.e. ~1084x711 of client area, which is why a vertical
  scrollbar was present from launch. minWidth/minHeight 640x480.
  A WINDOW_REVEAL_TIMEOUT_MS=5000 fallback shows the window even if
  measuring stalls, so show:false cannot itself become a no-window bug.
  fitToContent logs "[window] content WxH" and warns if overflow remains.
- Single-instance lock: losing the lock used to call app.quit() and vanish.
  Now the primary records {port,pid} in userData/instance.json (cleared on
  will-quit), and a launch that loses the lock HEAD-probes that port
  (6 attempts, 1s timeout, 500ms apart). Responding -> exit(0) silently,
  since the primary raises its own window. Not responding -> error dialog
  naming the taskkill command, then exit(1).
- startServer() now rejects after SERVER_START_TIMEOUT_MS=20000 so the
  primary can never sit windowless holding the lock forever.
- Verified all four paths: healthy primary (second launch exit 0 in 1s, no
  dialog); wedged primary simulated with a stub app that takes the lock and
  starts no server, plus a stale instance.json pointing at a dead port
  (dialog shown, exit 1); record written with the live port during a run and
  cleared on graceful quit; left behind on SIGKILL, which the probe handles.
